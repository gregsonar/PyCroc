# Ветвление, worktree и репозиторий

Правила этого раздела **важны для всех проектов** -- это базовая гигиена, которая
не даёт агенту сломать репозиторий и держит релизную ветку всегда стабильной.

## Модель веток

```
main   --o------------------------o----   <- только человек мёржит сюда;
          \                      /            всегда стабильная версия + теги
dev    ----o--o--o--o--o--o--o--o------    <- интеграционная ветка
               \        /
feature/<фича> -o--o--o-                   <- ветка на фичу, в отдельном worktree
```

## Правила

### 1. Агент ВСЕГДА работает в своём worktree

Чтобы не ломать основной репозиторий, агент ведёт работу в **отдельном git
worktree**, а не в основном рабочем каталоге. Основной чекаут остаётся
нетронутым; параллельные сессии/агенты не мешают друг другу; `git status` и
`git diff` чисты и относятся только к текущей работе.

Про **общий stash-стек**: worktree делят один stash с основным чекаутом. Не
использовать голый `git stash` / `git stash pop` -- можно снять чужие изменения.
Откладывать работу -- временным WIP-коммитом; если stash необходим -- именованный
(`git stash push -u -m "<уникальный-тег>"`) с восстановлением по SHA через
`apply`, не `pop`.

### 2. Каждая фича -- отдельная ветка

Все разработки ведутся в **отдельных ветках на каждую фичу**. В интеграционную
или релизную ветку напрямую не пишут.

Имя ветки: `feature/<slug>` (в этом проекте исторически `claude/<slug>-<hash>`).
**Хвост-хэш** обеспечивает уникальность имени: по умолчанию генерируется
инструментом автоматически, вручную указывается только при необходимости.

### 3. Путь фичи: feature -> dev -> main

```
фича готова
  -> все тесты прошли (гейт из трёх проверок, см. 01)
  -> ревью с человеком пройдено
  -> ветка мёржится в dev            (по умолчанию через PR, см. правило 4)
  -> ... накопление релиза в dev ...
  -> в main мёржит ТОЛЬКО человек    (по его решению; агент этого не делает)
```

- **`dev`** -- интеграционная ветка: сюда сходятся завершённые, протестированные
  и отревьюенные фичи.
- **`main`** -- **всегда только стабильная версия программы**. Мёрж `dev -> main`
  делает **только человек** и **только по своему решению** -- это событие релиза,
  а не рабочий шаг. Агент в `main` не мёржит никогда.

### 4. Pull Request -- по умолчанию; прямой push -- исключение

- **По умолчанию работа вливается через Pull Request.**
- **Прямой push -- исключение**: только по прямой команде владельца и после
  обсуждения.
- После PR в `dev` и проверки на отсутствие ошибок и конфликтов агент может
  **спросить** владельца о дальнейших шагах (например, о промоушене в `main`). В
  остальных случаях команду на слияние/релиз даёт владелец.

### 5. Происхождение файлов в worktree

В рабочем дереве могут появляться файлы, созданные **между сессиями** (другими
или прошлыми сессиями агента, либо владельцем по рекомендациям агента). Владелец
подтвердил: всё содержимое репозитория создано агентом или им самим по
рекомендациям агента. Такие файлы -- **не чужеродные**: их можно принимать после
проверки, а не отвергать как незнакомые. (Пример: `send_panel.py`/`file_picker.py`
были приняты так в Task 9.)

## Версионирование и теги

- **SemVer используется по умолчанию во всех проектах** (`MAJOR.MINOR.PATCH`).
- **Теги ставятся при сборке в релизные ветки** (`main`/`master`) и в `dev`.
  Релизный workflow (см. ниже) триггерится тегом вида `v*`, так что без тега
  релиз не соберётся.
- Простановку тега/релиза инициирует **человек** (это часть решения о промоушене
  в `main`).

## Гигиена репозитория

- **`.gitignore`** покрывает артефакты сборки, кэши инструментов, виртуальное
  окружение, БД и, отдельно, каталог `tmp/` -- рабочую песочницу (демо-скрипты,
  сырые дампы, конспект ручного тестирования). Содержимое `tmp/` намеренно **не
  версионируется**: это черновики процесса, а не артефакты проекта.
- Завершённые артефакты (план после закрытия всех задач) **перемещаются**, а не
  удаляются: `docs/plans/<план>.md -> docs/plans/completed/<план>.md`. История
  задач остаётся в репозитории.

## CI как второй контур гейта

CI (`.github/workflows/ci.yml`) повторяет ровно те же три проверки, что и
локальный гейт (линтер -> типизация -> тесты), и запускается:

- на каждый **pull request в `dev` и `main`**;
- на **push в `dev`**;
- на матрице ОС x версий языка (в проекте -- ubuntu/windows x Python 3.11/3.13).

Идея: локальный гейт -- основная защита, CI -- страховка, что в интеграционную и
релизную ветку не попадёт код, не прошедший проверки. Интеграционные тесты
используют заглушку вместо реального внешнего бинарника, поэтому CI не требует
сети и внешних зависимостей.

Релизный workflow (`release.yml`) -- **черновик, триггер по тегу `v*`**; шаги,
требующие секретов/учёток (публикация пакета, подпись), помечены как TODO и
выполняются владельцем, а не агентом.

## Перенос на другой проект

- Замените имена веток на свои (`dev`/`develop`/`integration`, `main`/`master`).
- Правила переносятся дословно: **агент всегда в своём worktree; фича -- отдельная
  ветка; PR по умолчанию, прямой push -- исключение; в main мёржит только человек;
  main всегда стабилен; SemVer + теги на релизах**.
- CI должен **дублировать локальный гейт один-в-один** -- иначе появляется класс
  ошибок «локально забыл прогнать».
