# Формат задач и багов

В проекте несколько потоков работы, у каждого своё место и форма:

1. **Плановые задачи** -- заранее спроектированный объём, чекбоксы в плане.
2. **Баг-репорты** -- структурированные, отслеживаемые дефекты; ведутся по скиллу
   **bug-report-tracker** (единый 14-польный формат, идентификаторы `BUG-###`).
3. **Черновой конспект ручного тестирования** -- сырые наблюдения по ходу живой
   проверки; по умолчанию остаются в песочнице `tmp/`.

Все потоки сходятся в коммитах (см. [03-commit-conventions.md](03-commit-conventions.md)).

---

## 1. Плановая задача (чекбоксы в плане)

Источник формата: [docs/plans/completed/pycroc-plan.md](../plans/completed/pycroc-plan.md).

Задача в плане -- блок из четырёх частей:

```markdown
### Task N: <краткое имя задачи>

**Files:**
- Create: <путь>, <путь>
- Modify: <путь>

- [ ] <шаг реализации>
- [ ] <шаг реализации>
- [ ] добавить тесты: <какие именно кейсы>
- [ ] запустить <команда проверки> -- должен пройти перед Task N+1
```

Правила формата:

- **Заголовок** `### Task N: <имя>` -- сквозная нумерация, задачи идут по порядку.
- **`**Files:**`** -- явный список создаваемых/изменяемых файлов ещё до начала
  работы (`Create:` / `Modify:`). Задаёт границы задачи.
- **Чекбоксы шагов** `[ ]` -> `[x]` по мере выполнения, отмечаются **прямо в
  плане**. Последний чекбокс задачи, как правило, -- **прогон проверки-гейта** с
  явной формулировкой «должен пройти перед Task N+1».
- **Решения по ходу** записываются курсивной вставкой прямо в задаче:
  `*(решение 2026-07-13: только из истории -- избранное планом не предусмотрено)*`.
  Так виден не только результат, но и почему выбран вариант.
- **Отклонения от первоначального плана** дописываются в скобках к чекбоксу:
  `*(выполнено скриптованно с croc v10.2.7: найдены и исправлены 3
  несовместимости ...)*`.

Верхнеуровневая структура самого плана (переносимый скелет):

```
# <Название>
## Overview             -- что это и что увидит пользователь в конце
## Context              -- факты, добытые разведкой (со ссылками на источник)
## Development Approach  -- правила процесса для этого плана
## Testing Strategy      -- что и как тестируется, «самый ценный тест»
## Solution Overview     -- архитектура, поток данных, design decisions
## Technical Details     -- контракты, сигнатуры, граничные случаи, тест-кейсы
## Implementation Steps  -- Task 1..N с чекбоксами
## Post-Completion       -- то, что нельзя автоматизировать (ручные/внешние проверки)
```

Отдельно ценно: в плане **граничные случаи специфичны для домена**, а не
абстрактны («handle empty input»), и к каждому разделу приложены **конкретные
тест-кейсы** с ожидаемым результатом ещё до написания кода.

## 2. Баг-репорт (скилл bug-report-tracker)

**Каноничный формат баг-репортов задаёт скилл `bug-report-tracker`** -- он и есть
источник истины, а не произвольная запись в чате или заметке. Ниже -- краткая
выжимка; при заведении бага работаем по самому скиллу.

### Куда складывать (решается при первом баге в проекте)

- Расположение: по умолчанию `.claude/bugs/` (можно `bugs/` или `docs/bugs/`).
- Режим хранения:
  - **single-log** (багов немного) -- всё в одном файле `<loc>/BUGLOG.md`, записи
    разделены `---`.
  - **index mode** (багов много) -- `<loc>/INDEX.md` (таблица-сводка,
    **регенерируется скриптом**, руками не править) + по файлу на баг
    `<loc>/BUG-<id>-<slug>.md`.
- Наличие `BUGLOG.md` vs `INDEX.md` само говорит о режиме -- следующим сессиям
  спрашивать заново не нужно.

### 14 полей (форма фиксирована)

Заголовок -- H1, поля 2-14 -- H2. Идентификатор `BUG-###` стоит в поле 1:
`# 1. Заголовок: [BUG-007] Короткое название`.

1. Заголовок `[BUG-###] ...` · 2. Подзаголовок (проект/подпродукт) ·
3. Компонент · 4. Версия · 5. **Критичность**: `Blocker | Critical | Low |
Trivial` · 6. **Приоритет**: `High | Medium | Low` · 7. **Статус**: `Open |
In Progress | Resolved | Closed` · 8. Автор репорта (LLM -- конкретная модель,
напр. «Claude Code (Sonnet 4.6)») · 9. На кого назначен · 10. Прикреплённые файлы
(*необязательное*, но заголовок оставить с `—`) · 11. Описание ·
12. Шаги воспроизведения (шаг + ожидаемый результат) · 13. Ожидаемый результат ·
14. Фактический результат.

Правила, критичные для консистентности:

- **Форму не менять** -- ни переименований, ни новых тиров (нет «Major»/«Medium»
  в критичности). Формат фиксирован намеренно, чтобы репорты оставались
  парсимыми и ссылаемыми.
- **ID сквозные и не переиспользуются** (даже после закрытия) -- это делает
  ссылку «см. BUG-004» стабильной. Следующий ID -- через
  `scripts/bug_tools.py next-id`.
- Чего не знаешь уверенно (компонент, версия, исполнитель) -- **спросить**, а не
  выдумывать: правдоподобное-но-ложное значение хуже честного `—`.
- **Статус обновляется в момент смены реальности**, не в конце сессии. В
  index-режиме после правки статуса в файле бага -- перегенерировать `INDEX.md`
  скриптом, а не править строку таблицы руками.

### Журнал работы над багом (после 14 полей -- свободная форма)

Датированные записи: попытки фикса, диагнозы, ограничения. **Связи между багами
указывать явно по ID** и кратко пояснять предполагаемую связь («Возможно связано
с BUG-004 -- там похожая ошибка кодировки»), а не оставлять подразумеваемой.

### Статусы (значение по умолчанию)

`Open` -- не начат · `In Progress` -- воспроизводится/чинится · `Resolved` --
фикс сделан, но не верифицирован · `Closed` -- проверен и закрыт.

## 3. Черновой конспект ручного тестирования

Сырые наблюдения по ходу живой проверки (как исторический `tmp/manual-testing-notes.md`)
**по умолчанию остаются на месте, в песочнице `tmp/` (вне git)** -- это важно для
самого процесса тестирования. Если такие заметки становятся значимыми для проекта,
их можно собрать в `docs/` в виде документов -- но **только когда это
действительно понадобится**, а не заранее. Это правило важно для всех проектов.

Связь потоков: тестируешь -> сырые наблюдения в `tmp/` -> то, что оказалось
реальным дефектом, оформляешь как **баг-репорт через трекер** (`BUG-###`) ->
закрываешь коммитом `fix(...)` со ссылкой на тест по имени.

---

## Как потоки связаны с коммитами

- Плановая задача -> коммит `feat/fix(...)(Task N)`.
- Баг -> коммит `fix(...)` со ссылкой `BUG-###` (или историческим `item N`).
- Каждый закрытый баг ссылается на **тест-кейс по имени** и, где уместно, на
  **gotcha** в заметках разработки (см. [05-documentation-and-style.md](05-documentation-and-style.md)).

## Перенос на другой проект

- Плановый формат (Files / чекбоксы / гейт-чекбокс / решения курсивом)
  переносится как есть, независимо от языка и стека.
- Баг-репорты ведите по скиллу `bug-report-tracker` -- единый формат и сквозные
  `BUG-###` важны именно для переносимости и кросс-ссылок между проектами.
- Черновые заметки тестирования держите в песочнице; промоутите в `docs/` только
  по мере необходимости.
