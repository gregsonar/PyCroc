# Процесс разработки: жизненный цикл задачи

## Суть

Работа идёт **по одной задаче за раз**, строго последовательно, по канoническому
плану. Каждая задача проходит полный цикл до конца -- и только потом начинается
следующая. Между задачами стоит ревью-гейт владельца процесса.

Источники: план [docs/plans/completed/pycroc-plan.md](../plans/completed/pycroc-plan.md)
(раздел «Development Approach»), git-история (по одному коммиту на задачу),
память процесса.

## Цикл одной задачи

```
взять следующую задачу из плана
        |
        v
реализовать (код)                 <- «код сначала, затем тесты», но тесты
        |                            обязательны в рамках ТОЙ ЖЕ задачи
        v
написать/обновить тесты для изменённого поведения
        |
        v
прогнать гейт из трёх проверок    <- тесты / линтер / типизация -- все чисто
        |
        v
обновить документацию, если задача этого требует
        |
        v
отметить чекбоксы в плане
        |
        v
остановиться и ждать ревью        <- «Ревью ок, переходи к Task N»
        |
        v
закоммитить (один коммит на задачу)
        |
        v
следующая задача
```

## Правила, которые здесь соблюдаются

### 1. Одна задача доводится до конца перед началом следующей

Задача считается закрытой, только когда сделаны **код, тесты, документация и все
проверки зелёные**. Частично закрытых задач в истории нет -- каждая плановая
задача (Task 1..16) имеет ровно один коммит и все свои чекбоксы отмечены.

### 2. Код сначала, тесты -- обязательны в той же задаче

Порядок «сначала код, потом тесты» допускается, но **тест не откладывается на
потом**: любая задача, меняющая поведение, включает тесты до перехода дальше.
Это требование не зависит от того, в каком порядке физически написаны строки.

### 3. Гейт из трёх проверок

Перед переходом к следующей задаче прогоняются и должны быть **чисто все три**:

```bash
pytest -q
ruff check .
mypy src --strict
```

(Команды из этого проекта; на другом проекте -- эквивалентные тесты, линтер и
статическая проверка типов.) Это жёсткий гейт: «КРИТИЧНО: все тесты должны
проходить перед началом следующей задачи» -- формулировка из плана. Тот же набор
дублирован в CI (см. [02-branching-and-worktrees.md](02-branching-and-worktrees.md)),
чтобы гейт нельзя было обойти.

### 4. Ревью-гейт между задачами

После завершения задачи агент **останавливается и ждёт явного ревью** владельца
(«Ревью ок, переходи к Task N»), а не переходит к следующей самостоятельно.
Задачи не «пакетируются» -- владелец видит результат каждой прежде, чем начнётся
следующая.

### 5. При неочевидном решении или противоречии -- спросить, не решать самому

Если задача противоречит плану, или возникает неочевидное архитектурное решение,
-- агент **останавливается и спрашивает**, а не выбирает вариант молча. Пример из
плана: решение «автодополнение кода только из истории (избранное планом не
предусмотрено)» и «хранение кодов открытым текстом» -- оба вынесены на явное
решение, а не приняты по умолчанию (см. отметки решений прямо в тексте задач
плана).

### 6. Устойчивость важнее обратной совместимости

Обратная совместимость самого проекта может быть неактуальна (новый проект), но
код, завязанный на внешний нестабильный контракт, обязан **деградировать мягко**:
не падать на неизвестном входе, а игнорировать его с диагностическим логом. В
PyCroc это парсер вывода croc (формат меняется между версиями) -- правило
«нераспознанная строка -> `None`, не исключение». Универсальный принцип: на
границе с внешней системой, которую ты не контролируешь, отказ парсинга -- это
штатная ветка, а не краш.

## Перенос на другой проект

- «Три проверки» = {автотесты, линтер, статический анализ/типизация} вашего
  стека. Конкретные команды меняются, роль гейта -- нет. Конкретный линтер
  обязателен только тогда, когда он определён в самом проекте (см.
  [05-documentation-and-style.md](05-documentation-and-style.md)).
- «План с задачами» = любой упорядоченный список задач с явными критериями
  готовности (см. [04-tasks-and-bugs.md](04-tasks-and-bugs.md)).
- Ревью-гейт применим и без ИИ-агента: это просто правило «не начинать
  следующую единицу работы, пока предыдущая не принята».
