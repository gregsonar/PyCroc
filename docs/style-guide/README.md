# Style guide процесса разработки

Этот набор документов описывает, **как ведётся разработка** -- не что делает код,
а как устроен процесс: ветвление, задачи, баги, коммиты, документация, проверки.

Правила извлечены из реальной истории проекта PyCroc (git-история, план задач,
заметки, ручное тестирование) и подтверждены владельцем процесса. Это не
абстрактные «best practices из воздуха»: где в истории правила не было, оно либо
получено явным решением владельца, либо вынесено в
[open-questions.md](open-questions.md) как открытый вопрос, а не додумано.

Документы написаны так, чтобы их понял и человек-разработчик, и ИИ-агент, впервые
открывший проект. Они **универсальны** -- применимы к другим проектам, а не
только к PyCroc/croc/Textual. Правила, помеченные как «важно для всех проектов»,
переносятся как есть.

## Где что лежит (соглашение о расположении)

- **`README.md` и `CONTRIBUTING.md` -- в корне проекта** (так принято в
  большинстве проектов, там их ищут по умолчанию).
- **Документация проекта -- в `docs/`.**
- **Этот style-guide -- в `docs/style-guide/`**, `CONTRIBUTING.md` в корне может
  на него ссылаться.

Style-guide -- живой документ: при **санкционированных и обсуждённых** с
владельцем изменениях процесса правятся и сами эти файлы, иначе они устареют.

## Три принципа, на которых держится всё остальное

1. **Одна задача доводится до конца, прежде чем начата следующая.** Задача -- это
   код + тесты + документация + прохождение всех проверок. Полузакрытых задач в
   истории нет.
2. **Проверки -- это гейт, а не вежливость.** Переход к следующей задаче
   запрещён, пока тесты, линтер и типизация не чисты. То же дублируется в CI,
   чтобы гейт нельзя было обойти по забывчивости.
3. **Знание фиксируется письменно в момент, когда оно получено.** Неочевидные
   выводы (gotchas), диагнозы багов и принятые решения записываются в
   предназначенные для этого места сразу, а не восстанавливаются потом из памяти.
