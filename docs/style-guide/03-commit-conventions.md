# Соглашения о коммитах

Правила извлечены из реальных сообщений `git log` (все ветки) и уточнены
владельцем. Это **не общий шаблон Conventional Commits из документации**, а тот
срез, который фактически используется.

## Заголовок: Conventional Commits + ссылка на задачу

Формат:

```
<type>(<scope>): <краткое описание в повелительном/настоящем времени> (<ссылка на задачу>)
```

### Типы (`type`) -- только эти встречаются в истории

| type | Когда |
| --- | --- |
| `feat` | новая функциональность |
| `fix` | исправление поведения |
| `docs` | только документация (README, CHANGELOG, notes, план) |
| `chore` | обслуживание (scaffolding, правки `.gitignore`) |
| `ci` | пайплайны/инфраструктура сборки |

Незнакомых типов (`refactor`, `test`, `perf`, `style`, `build`) в истории **нет**
-- не значит, что запрещены, но по умолчанию держимся минимального набора выше.
Тесты не выделяются в отдельный тип: они входят в `feat`/`fix` той же задачи (см.
[01-development-process.md](01-development-process.md)).

### Скоуп (`scope`) -- по слою архитектуры

Используется скоуп-слой: `core`, `storage`, `ui`. Совпадает с делением пакета
(`pycroc/core`, `pycroc/storage`, `pycroc/ui`). `docs`/`chore`/`ci`-коммиты
обычно **без** скоупа. Универсальный принцип: скоуп = имя подсистемы, которую
задача затрагивает.

### Ссылка на задачу в конце заголовка

Заголовок **привязан к единице работы** одним из способов, как в истории:

- `(Task 2)` -- плановая задача из [плана](../plans/completed/pycroc-plan.md);
- `(item 8)` -- находка ручного тестирования / баг;
- `(items 11/14)` -- коммит закрывает несколько связанных находок сразу.

Когда баг ведётся через трекер (см. [04-tasks-and-bugs.md](04-tasks-and-bugs.md)),
в ссылке уместен его идентификатор `BUG-###`.

Реальные примеры заголовков:

```
feat(core): add CrocOptions and CLI argument builders (Task 2)
fix(core): kill the whole croc process tree on cancel (items 11/14)
feat(ui): show total size of the selection in SendPanel (item 9 remainder)
docs: write README and CHANGELOG for 0.1.0 (Task 15)
ci: add CI and draft release workflows + module entry point
```

## Тело коммита

Тело **обязательно для содержательных `feat`/`fix`** и имеет устойчивую
структуру (примеры -- `git show b0c45ed`, `a957d4c`, `850e63b`):

1. **Что и почему** -- проблема/контекст первыми строками. Для багов --
   **root cause** явным образом («Root cause of ...»).
2. **Fix** -- что сделано, при нескольких изменениях -- маркированным списком.
3. **Verification** -- как проверено (в т.ч. на реальном внешнем инструменте, с
   конкретными числами: «cancel() dropped from 5.01s to 0.14s»).
4. **Строка `Tests:`** -- какими тест-кейсами закрыто, **по именам** (см. правило
   ссылки на тесты в [05-documentation-and-style.md](05-documentation-and-style.md)).

Скелет:

```
<type>(<scope>): <заголовок> (<ссылка на задачу>)

<1-3 абзаца: контекст и, для бага, root cause.>

Fix:
- <изменение 1>
- <изменение 2>

<Verification: как проверено, желательно с измеримым результатом.>

Tests: <имя_кейса_1>; <имя_кейса_2> (<путь к файлу теста>).
```

## Никаких лишних трейлеров

**Трейлер `Co-Authored-By: Claude ...` не добавляется.** Авторство и происхождение
коммита уже фиксируются другой метаинформацией (git-автор/коммиттер, метаданные
сессии). Не дублировать это лишней строкой в теле -- **не добавляем лишнего без
необходимости**.

> Историческая заметка: часть уже сделанных коммитов содержит такой трейлер.
> Историю мы не переписываем ради его удаления -- правило действует **вперёд**:
> в новых коммитах трейлера нет.

## Язык

- **Заголовок и тело коммита -- на английском.**
- Проза внутри репозитория (комментарии, docstring, план, notes, README,
  CHANGELOG) -- **на русском**. Причины этого раздвоения -- в
  [05-documentation-and-style.md](05-documentation-and-style.md).

## Гранулярность и правила git

- **Один коммит на задачу.** Плановая задача = один коммит; находка/баг = один
  коммит.
- Коммит создаётся **после ревью** соответствующей задачи, не раньше.
- Коммитить, пушить, открывать PR, ставить теги, мёржить -- **только по явной
  команде владельца** (см. модель веток и правило про PR в
  [02-branching-and-worktrees.md](02-branching-and-worktrees.md)). Агент не
  мёржит в `main` никогда.
- Предпочитать **новый коммит** правке (`--amend`) уже существующего.
- **Без эмодзи** в сообщениях коммитов (см. правило «без эмодзи» в 05). В истории
  коммитов эмодзи нет.

## Перенос на другой проект

- Набор `type` можно расширить под свой процесс, но зафиксировать закрытым
  списком, а не «как придётся».
- `scope` = ваши подсистемы.
- Переносится дословно: **привязка заголовка к единице работы**, **root cause +
  verification + `Tests:` в теле**, **один коммит на задачу**, **без лишних
  трейлеров**.
